## 1. 增量式、异步安全的 Attention Plan

**待验证的核心命题：** request 加入/退出、KV 页增长与 speculative acceptance 通常只改变一部分计划。如果能只更新变化部分，并保证多步异步执行不会覆盖尚在使用的 metadata/workspace，可减少调度关键路径上的 host 工作、同步和 GPU 等待，同时保持数值正确与图回放。实现需要引擎的计划生命周期协议与 GPU 工作队列/kernel 一起改变。

**近邻边界：** [FlashInfer MLSys 2025](https://proceedings.mlsys.org/paper_files/paper/2025/hash/dbf02b21d77409a2db30e56866a8ab3a-Abstract-Conference.html)已有动态负载均衡和图兼容；[Blackwell GPU planner 讨论](https://github.com/orgs/flashinfer-ai/discussions/1743)说明 GPU 端规划已有实现方向；[MOIRA 预印本](https://arxiv.org/abs/2610.04313)已有 vLLM 中的 self-planning attention。[vLLM #61239](https://github.com/vllm-project/vllm/issues/61239)中双缓冲/事件也是已提出的竞态修复。论文不能把“GPU planner”或“加双缓冲”单独称为新意；可能成立的差异在**跨请求/跨步增量更新及严格的异步发布—消费—回收机制**。

**第一轮实验：** 锁定 vLLM/FlashInfer 版本，在真实 Qwen3-8B 服务中对低/高 request churn、chunked prefill、prefix 命中和支持的多 token draft 分别测 `plan()`、metadata、D2H/H2D、GPU idle、TPOT、TTFT、吞吐、P95 及数值正确性。比较现有 fast path、完整重建、仅修 race 的双缓冲与目标 GPU planner。只有目标成本在真实关键路径且简单对照不能解决时，才继续实现增量机制。这个顺序是降低租卡浪费，不预设负结果。

**A 会论文要求：** 提供计划增量算法与并发生命周期契约；在强基线、真实请求分布和至少两个主流引擎中证明何时有效与何时无效。若只修复一个 issue，定位为上游 PR。

## 2. 混合有状态模型的图安全 Prefill

**待验证的核心命题：** 在 GDN 与 full attention 交替的模型中，动态 prefill 的状态槽位与临时缓冲可以通过图内设备更新和固定地址协议处理，减少逐层 graph break 的 host 空隙。[SGLang #35851](https://github.com/sgl-project/sglang/issues/35851)在单 H200 的真实 Qwen3.5-35B-A3B FP8 服务中报告显著 GPU idle，单独融合 GDN kernel 未带来端到端收益；这只是公开报告，不是我们的 H20 结果。

**论文边界：** 做可复用的状态/图捕获契约，覆盖不同 chunk/batch、prefix 与 preemption，比较 vLLM 已有图路径；不能只关闭 SGLang 的单个 issue。[Marconi](https://proceedings.mlsys.org/paper_files/paper/2025/file/7c180af017258d239bac6248d1eb26ac-Paper-Conference.pdf)等工作已研究混合模型缓存复用。本题仅在首选题失去关键路径价值，或首轮复现显示更强的可泛化瓶颈时启动。

## 3. 混合模型的角色感知缓存与执行

**待验证的核心命题：** full attention、滑窗、recurrent state 与 draft state 的生命周期不同，统一缓存池可能迫使引擎预留过多空间，进而压低有效并发。[vLLM #59117](https://github.com/vllm-project/vllm/issues/59117)给出单 A800 的真实容量下降案例，但该 issue 已有独立 draft pool 的 POC；[vLLM Q4 2026 roadmap](https://github.com/vllm-project/vllm/issues/61024)也列有可插拔 cache config 与分组改进。因此“给 draft 单独分池”不是新论文方法。若研究此题，必须把不同缓存生命周期、调度可见容量与算子执行统一建模，至少在两种混合架构上显示相同机制。当前没有足够证据让它挤占首选题资源。

## 硬件与仓库边界

- A100 PCIe 40GB、A800 80GB、H20 96GB 都是有效的生产级单卡实验平台；显存和后端支持决定模型/上下文规模。第一轮以可租到且最省钱的适配卡起步，按相同 GPU 比较基线与改动。
- [DeepGEMM 当前要求 SM90/SM100](https://github.com/deepseek-ai/DeepGEMM)；只有 H20/H800 等相应卡可直接运行其现有实现。它可用于后续 Hopper 算子对照，不自动成为上面三个题的必需依赖。
- [DeepInfer 当前开源版](https://github.com/deepseek-ai/DeepInfer)只支持 DeepSeek-V4.1-Flash 和 SM100/Ascend 950，官方性能配置为多卡，适合作设计参考，不作为单 H20/A800 的端到端实验框架。
- 所有公开论文/issue 的测量与本项目待测结果分开记载；本项目需要重新采集目标 GPU 的正确性与端到端性能证据。
