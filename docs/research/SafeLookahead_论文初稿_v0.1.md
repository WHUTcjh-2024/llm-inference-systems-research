# Safe Lookahead：动态图化推理中的安全重叠深度

> 工作稿，2026-11-01。本文记录已完成的实验与待验证的方法。Gate 0 尚未作出决策；本文不声称已实现所述机制，也不报告端到端加速。

## 摘要

异步调度允许大模型推理引擎在设备执行当前批次时准备后续批次。CUDA Graph 减少了部分主机端开销，但动态图化路径仍涉及随批次变化的元数据、执行计划和工作空间。主机能够领先设备多少个调度步，既受这些对象的生命周期约束，也受前一步设备输出的依赖约束。本文将这一数量定义为安全重叠深度，并提出按资源约束与依赖约束分别归因的测量框架。在此基础上，我们研究面向 attention plan 的多版本管理，以及图执行与版本槽之间的绑定方式。当前 H20 实验表明，多个 CUDA Graph executable 不会自动隔离其引用的外部缓冲区；显式重绑定可在受控微基准中避免共享缓冲区污染。一次 vLLM 负载探测观察到深度为 2、GPU 步间空档较小，但尚未经正式重复、Nsight 时间线和多进程对照验证。这些初步观察提示：扩大版本槽数量之前，必须先确认目标负载中的空档是否由资源生命周期造成，以及额外重叠是否具有端到端价值。本文据此给出可证伪的实验协议，而非预设性能结论。

## 1 引言

大模型推理服务按批次调度请求，主机准备调度与算子元数据，设备执行对应计算。异步调度可以把相邻步骤的工作重叠起来；vLLM 的文档描述了在设备执行步骤 N 时准备步骤 N+1 的方式，并使用占位 token 处理尚未返回的结果 [1]。这一优化也使运行时必须同时管理多个步骤引用的状态。如果主机改写某一缓冲区时，设备仍在读取旧内容，就可能产生错误；如果为避免错误而等待设备完成，重叠又会缩小。

CUDA Graph 为这一问题增加了约束。一个 graph executable 的重复 launch 会按序执行；并发执行要求多个 executable。同时，节点参数可以更新，但参数更新和对象生命周期必须与执行顺序协调 [2]。因此，复制 graph executable 并不等于复制它引用的数据。对于随批次改变的 attention plan 或 metadata，安全性取决于主机写入、设备读取和槽位回收的具体时刻。

本文关注一个比“是否开启 async”更细的问题：在给定负载和显存预算下，引擎实际能保持多少个未完成的调度步？其中有多少领先深度因可变对象的槽位不足而损失，又有多少是因为后续步骤必须等待采样结果等设备输出？我们把前者记为资源限制 `k_res`，后者记为依赖限制 `k_dep`。版本池只能处理前者。如果测量发现后者主导，增加版本槽不会解决瓶颈。

我们的研究目标是先建立逐步时间线与等待归因，再在确有资源限制的路径上评估 plan 多版本机制。当前完成的受控实验排除了“克隆 executable 自动隔离 buffer”这一假设；一次负载探测反而显示现有异步执行可能已经隐藏大部分主机工作。因此，本文的核心机制仍是一项待检验的假设。论文是否进一步发展为性能机制工作，取决于正式实验能否发现可归因、可消除且足够大的残余空档。

## 2 问题与执行模型

本文的一个 `step` 是引擎对当前批次的一次调度与执行，不等同于单个请求生成一个 token。令 `k_actual(t)` 表示时刻 `t` 已准备而设备尚未完成消费的步骤数。更大的 `k` 需要为各步骤保留仍在使用的可变状态，也要求后续调度所需的信息已经可用。

我们区分两类上界。`k_res` 由 plan、metadata、workspace 等对象的版本槽及其显存成本决定；`k_dep` 由步骤之间必须等待的设备结果决定。有效深度不能超过两者中较小的上界。这个分解是测量假设，不能仅根据 host 函数调用次数推断：主机提前调用调度器，不代表 GPU 上已有同样数量的真实 in-flight step。实验必须对齐主机日志、CUDA 事件和设备时间线。

对于可复用缓冲区，需要维护至少三个顺序关系：写入新版本先于相应设备读取；旧版本的设备读取完成先于槽位复用；执行图引用的地址在消费期间保持有效。任何一个关系被打破，都可能使旧步骤读到新内容，或使新步骤访问被提前复用的状态。本文首先研究较小的 plan/metadata 对象；KV block 与 recurrent state 的生命周期问题只作为后续扩展，不计入首阶段机制效果。

## 3 方法设想

### 3.1 测量与归因

每个步骤记录主机准备阶段、设备执行区间、等待点、所引用的版本槽和释放事件。设备时间线用于测量相邻步骤之间的空档；主机插桩用于解释空档附近发生了什么。一次等待只有在能追溯到具体对象无可用槽位或尚未完成回收时，才归入 `k_res`；等待采样 token 或其他前序设备结果归入 `k_dep`。队列容量、Python 调度和插桩导致的额外等待单独报告。

这种归因先于机制实现。如果当前异步路径已经使 GPU 基本连续工作，进一步增大 `k` 即使可行，也未必改善端到端指标。若确有空档，还须证明它出现在计划复用相关的路径，而非由计算依赖或实验配置造成。

### 3.2 Plan 多版本

候选机制为 plan/metadata 维护有限个版本槽。主机仅写入可用槽；每次执行绑定其对应版本；设备消费完成后，该槽才重新进入可用集合。版本号和完成事件共同决定回收时刻。显存预算限制槽数，目标是在正确性与预算约束下减少由槽位不足造成的等待。

首个可行性实现考虑多个 graph executable 与显式重绑定的外部缓冲区。它用于验证多步骤并行与生命周期协议，不能直接代表最终方案。后续若证据支持这一方向，再比较节点参数更新、静态版本池与单图多版本 ABI 的成本。CUDA 文档说明同一 executable 的 launch 按序执行，而不同 executable 可用于并发 [2]；这些 API 语义不能替代真实引擎中的地址与生命周期验证。

### 3.3 正确性条件

机制需要保证两个不变量：设备读取的版本与该步骤提交的版本一致；任何槽位被重新写入之前，所有旧消费者均已完成。研究计划用一个包含两个版本槽的有限状态模型检查提交、读取与回收顺序，并用受控延迟放大可能的竞态。模型检查覆盖抽象协议；它本身不能证明完整 vLLM 与 FlashInfer 实现没有缺陷。

## 4 已完成的初步实验

### 4.1 Graph executable 与缓冲区隔离

在单卡 H20 的受控 CUDA 微基准中，含图内 allocation/free 节点的图第二次实例化返回 `cudaErrorNotSupported`。对于图外缓冲区，两个 executable 默认保留同一捕获指针；在共享指针并发回放的 200 次测试中，200 次出现数据污染。显式为第二个 executable 重绑定独立缓冲区后，200 次并发测试未观察到污染；Nsight 节点时间线确认并发组的 kernel 发生重叠。两个 executable 的实例化显存增量合计约 2 MiB，外部缓冲区另行分配。该结果证明“克隆即可隔离”不成立，也只证明受控微基准中的重绑定路径可行，尚不能外推为 vLLM 端到端收益 [3]。

### 4.2 vLLM 负载探测

一次 mixed prompt、8 条请求的 smoke 在 vLLM 0.29.0、FlashInfer 0.6.18 与 Qwen3-8B 上运行。按记录中的 decode step 统计，`k_actual` 中位数与最大值均为 2；残余主机工作中位数约 1.405 ms，设备步骤时间中位数约 6.211 ms。测量跨度内的 GPU 步间空档合计约 3.26 ms，占 0.64%。该探测使用同进程采集路径，仅有一次有效样本，尚无对应的 Nsight 验证及未插桩的多进程对照。因此，这些数字只能说明应优先排查“现有深度已足够隐藏主机工作”的可能性，不能据此判定 Gate 0 通过或失败 [3]。

当前源码与插桩记录还显示，等待采样输出的 future 是重要等待点，而本次负载未出现 KV block 压力。这支持进一步调查 `k_dep`，但不构成正式的 `k_res`/`k_dep` 定量归因 [3]。

## 5 后续评估协议

正式 Gate 0 将在固定模型、版本与请求配置下，对 uniform、mixed/ragged 及关闭 async 的对照重复运行，并以 Nsight 校准设备执行区间、GPU 空档和同步点。多进程的干净运行用于估计插桩路径对重叠与吞吐的扰动。每个配置至少重复三轮，报告中位数、离散程度、尾延迟及原始运行配置 [3, 4]。

若正式结果显示可归因于 plan/metadata 生命周期的空档，再实现最小版本池，并与当前 async、同步、静态双缓冲及节点参数更新等简单方案比较。主要性能指标为既定 TTFT/TPOT SLO 下的 goodput，同时报告显存、P95 延迟和正确性违反次数。微基准并发时间、主机工作占比与端到端收益分别报告，避免把任何一个代理指标当作最终性能结果。

若 `k_dep` 主导，版本池机制的目标就不成立；若现有异步路径已把 GPU 空档压到很小，研究应转向归因与诊断工具，或重新选题。预注册的数值门槛及完整止损条件见研究协议 [4]；正式数据之前不据这些门槛作结论。

## 6 讨论与局限

目前最关键的不确定性不是版本槽能否正确实现，而是它是否解决真实的性能瓶颈。现有 smoke 同时呈现较高的主机工作占比与很低的 GPU 步间空档，说明“主机仍在工作”和“设备仍在等待”不能画等号。另一个边界是 mixed/ragged 负载的实际可变对象：其关键路径可能位于引擎的 attention metadata builder，而非 FlashInfer decode plan。正式机制设计须服从这一归因结果。

现有数据来自单卡 H20 和一个小规模 smoke；受控微基准采用人为拉长的 kernel。由此不能推断其他 GPU、请求规模、图模式或真实服务流量下的收益。尤其不能把两个独立 executable 在微基准中的并发，写成安全重叠深度机制已在生产引擎中成立。

## 7 结论

安全重叠深度同时受对象生命周期和执行依赖限制。本文提出先测量、再归因、最后决定是否实施多版本机制的研究路径。已完成实验澄清了 CUDA Graph executable 克隆与外部缓冲区隔离的关系；初步负载探测则使机制的性能前提保持开放。只有正式实验显示资源生命周期造成可消除的端到端损失，Safe Lookahead 才适合作为性能机制论文继续推进。
