# 主流推理引擎与算子：A 会选题跨年复审

复审日期：2026-10-21。研究资源：每天约两小时；按需租用 AutoDL 的 A100 PCIe 40GB、A800 80GB、H20 96GB 等生产级单卡。本文是**选题与实验决策**，不是已有论文结果。本项目尚无这些题目的 GPU 实测数据。

## 摘要与研究问题

问题不应限定为 DashAttention 或某一个小仓库。真正值得研究的是生产引擎与高性能算子之间的动态执行契约：引擎每步改变 batch、KV 页和状态，算子却希望稳定的调度计划、内存地址和 CUDA Graph。这个矛盾同时出现在 vLLM/FlashInfer 的异步 attention planning 与 SGLang 混合 GDN 模型的 prefill 图断点。两条路线都有实码入口、真实模型和可以单卡验证的工作负载；没有一条已经被证实可形成 A 会论文。

- **RQ1：** 2023–2026 年的强工作已覆盖哪些算子/引擎机制，剩下的机制空白是什么？
- **RQ2：** 哪个问题能在 vLLM/SGLang + FlashInfer/FlashAttention/DeepGEMM 的实际路径形成算子与引擎共同贡献？
- **RQ3：** 哪些 AutoDL 生产卡足以证实单卡结论，第一轮应该测什么？

方法：以会议正式论文、项目官方代码/文档和维护者 issue 为主要证据；论文已发表、预印本、公开 issue、本文假设分别标注。检索范围不限定 2026 年。未检索到同题论文并不等于证明新颖性。

上述先例覆盖的是不同层次。它们约束“通用融合/调度”的空泛提法，却不排除**每步变化的计划如何在 GPU 上安全增量更新**，或**有状态混合层何时能够连续图回放**这样的具体问题。

## 二、首选题：增量式、异步安全的 Attention Plan

**一句话机制：** 把 attention 的执行计划改成设备端固定地址、按 request/KV 页变化量更新的版本化工作队列；引擎用明确的生产者—消费者生命周期交付计划，算子按版本消费，让连续批处理与投机解码避免每步完整重建、阻塞式 D2H 和 workspace 竞态。

**痛点证据。** [FlashInfer 源码](https://github.com/flashinfer-ai/flashinfer/blob/main/include/flashinfer/attention/scheduler.cuh)仍存在主机 planner 与 pinned-buffer 异步拷贝路径。[vLLM #29134](https://github.com/vllm-project/vllm/issues/29134)说明 FlashInfer `plan()` 中的主机/设备转换阻碍完全异步的多 token 推测解码；[#49488](https://github.com/vllm-project/vllm/issues/49488)报告多步 draft 反复重建 metadata 及 host launch 空隙；[#61239](https://github.com/vllm-project/vllm/issues/61239)则记录去掉隐式同步后，下一步覆盖上一条尚在使用的 plan/workspace，触发非法访问。这些是公开报告，**不是本项目测量**。

**可以投稿的技术内核。** 先定义 request 加入/退出、KV 页增长、prefix 命中、speculative acceptance 对工作计划的最小 delta；设计稳定索引与版本化发布协议（旧版本直到消费者完成才可回收）；在 GPU 上构造/修补 CTA 工作队列，并让 attention kernel 从当前已发布版本读取。必须同时研究何时 delta 更新划算、何时应完整重建，及 CUDA Graph 捕获下的地址与生命周期约束。只给 `plan()` 加双缓冲是 issue 已提出的修补建议，不能作为论文贡献。

**代码与验证对象。** 算子主体在 [FlashInfer](https://github.com/flashinfer-ai/flashinfer)，首先接入 [vLLM 的 FlashInfer backend](https://github.com/vllm-project/vllm/blob/main/vllm/v1/attention/backends/flashinfer.py)，再以 [SGLang 的 FlashInfer backend](https://github.com/sgl-project/sglang/blob/main/python/sglang/srt/layers/attention/flashinfer_backend.py)验证接口普适性。Qwen3-8B 提供 GQA 服务基线；DeepSeek-V2-Lite 提供 MLA/MoE 生产家族的真实模型，但必须核实选定版本的后端支持。不把 DeepInfer 当单卡直接验证对象。

**必须正面对照。** FlashInfer 默认 planner、SGLang 已有 `fast_prefill_plan`、固定计划/完整重建、仅双缓冲修 race，以及若目标卡支持的现有 GPU planner。[FlashInfer MLSys 2025](https://proceedings.mlsys.org/paper_files/paper/2025/hash/dbf02b21d77409a2db30e56866a8ab3a-Abstract-Conference.html)已有动态负载均衡和图兼容；[FlashInfer 开发者讨论](https://github.com/orgs/flashinfer-ai/discussions/1743)说明 Blackwell 已开始 GPU planner，并考虑移植到 Hopper/Ampere；[MOIRA（2026-10 预印本）](https://arxiv.org/abs/2610.04313)已在 vLLM 的稀疏长上下文解码中使用 self-planning attention kernel；[PersistentKV（2026 预印本）](https://arxiv.org/abs/2606.26666)已有 page-aware decode 工作队列。因此“GPU 端规划”本身不是新意。可投稿的差异应是**跨请求与跨步的增量更新 + 异步安全发布/回收 + 生产引擎端到端效果**，且需比较直接移植现有 GPU planner。需要测 planner CPU 时间、D2H/H2D、GPU idle、计划更新代价、TPOT、吞吐、P95 延迟和数值正确性，并测高 churn 与低 churn 两端；收益可能只在其中一端成立。

**风险和投稿门槛。** 如果现有 fast path 已令 plan 不在关键路径，或 device delta 建造成本更高，题目应改向；若只修一处 race，价值是高质量 PR。冲 CCF A 系统会议 ASPLOS/OSDI 的版本需要：形式化生命周期契约、通用更新算法、至少一个主流引擎内显著端到端效果、另一引擎复现机制、真实服务 trace 与失败边界。MLSys 是相关领域的重要会议，但它与 CCF A 分类不是同一个概念。这里列的是投稿证据要求，不是效果承诺。

## 三、第二题：混合有状态模型的图安全 Prefill

**一句话机制：** 为 GDN/线性注意力与 full attention 交替的模型定义可捕获的状态更新契约：哪些 index、临时张量和 persistent recurrent state 可以保持固定地址，哪些随请求/chunk 变化的数据只能由图内设备端更新；据此让 prefill 从逐层 graph break 转为连续图回放，并保持 preemption/prefix/speculation 下的状态正确。

**痛点证据。** [SGLang #35851](https://github.com/sgl-project/sglang/issues/35851)报告 Qwen3.5-35B-A3B FP8 在单 H200 的 prefill 因逐层 graph break 约一半时间 GPU 空闲；将 GDN 的 5-kernel 路径换成单 fused kernel，端到端吞吐仍未改善。这个反例说明单独优化算子内部可能无效。相对地，[vLLM 官方 tracker](https://github.com/vllm-project/vllm/issues/38175)说明其 decoder 已支持 CUDA Graph；Qwen3.5 的具体 prefill 捕获范围需要在固定版本中实测，不能声称“所有引擎都没有混合模型图路径”。

**技术路线。** 选择 Qwen3.5-9B 或 35B-A3B 的真实开源权重。先复制 SGLang 的 eager/breakable/full 可用执行路径，区分图断点前的 Python metadata、state-slot 映射、算子临时内存与内核。提出可复用的 `state update → attention/GDN → commit` 图内协议；必要时重写 GDN prefill 包装或小算子，但目标是消除图边界的 host idle。比较同一模型的 vLLM 实现，识别其可迁移机制，而不是忽略竞争方案。

**强先例与冲突风险。** [Marconi](https://proceedings.mlsys.org/paper_files/paper/2025/file/7c180af017258d239bac6248d1eb26ac-Paper-Conference.pdf)已解决一部分混合模型 prefix state 复用；[SpecLA（2026 预印本）](https://arxiv.org/abs/2607.16673)处理线性注意力模型的 speculative state；通用动态图 fusion 也已有 [Event Tensor](https://proceedings.mlsys.org/paper_files/paper/2026/hash/53d3f45797970d323bd8a0d379c525aa-Abstract-Conference.html)。本题的论文差异必须是**动态 prefill 中有状态层的图捕获条件、正确执行协议和引擎收益**。只关闭 #35851 是 PR；跨 chunk、batch 变化、状态复用和至少两种混合模型证明通用性，才有 A 会可能。

**比首选题更强的地方与代价。** 公开 issue 给出了很大的真实瓶颈，适合大胆切入；但可泛化的模型/后端测试矩阵更复杂，较难在每天两小时内迅速形成完整论文。因此作为并行概念储备，先做一轮定界复现，不同时实现两套系统。

## 四、仓库和硬件的真实边界

| 仓库 | 在方案中的角色 | 当前可租单卡能做什么 |
|---|---|---|
| vLLM、SGLang | 生产推理引擎、端到端主验证 | A100/A800/H20 均可运行适当规模模型；固定版本和后端。 |
| FlashInfer、FlashAttention | attention 基线与新 kernel 接口 | A100/A800/H20 具备实际意义；按架构用强基线，不能拿某卡默认弱后端制造收益。 |
| DeepGEMM | Hopper/Blackwell 的 MoE/GEMM 对照或后续算子线 | [当前官方实现要求 SM90/SM100](https://github.com/deepseek-ai/DeepGEMM)，H20/H800 可考察；A100/A800 不能直接运行当前 DeepGEMM。 |
| DeepInfer | 生产系统设计参考 | [开源版目前限制 DeepSeek-V4.1-Flash 与 SM100/Ascend 950](https://github.com/deepseek-ai/DeepInfer)，官方性能配置为多卡；单 H20/A800 不能据此声称完成其端到端验证。 |

A100 PCIe 40GB 是真的 A100 数据中心卡，不是玩具卡。先做首选题的 Qwen3-8B 服务与 FlashInfer 计划 profiling，可优先租价格/库存合适的 A100；长上下文或 DeepSeek-V2-Lite 优先 A800 80GB；H20 96GB 用于 SM90、DeepGEMM 和跨架构验证。单卡卡名中的 NVLink 不提供本研究单卡贡献。具体 AutoDL 库存/价格随时变动，以租用时页面为准。[DeepSeek-V2-Lite 官方模型卡](https://huggingface.co/deepseek-ai/DeepSeek-V2-Lite)说明 BF16 单卡 40GB 的最低要求，但 A100 40GB 对 KV 与服务开销余量很小；请勿据此承诺长上下文可运行。

## 五、启动顺序：把大胆题目变成可证伪实测

1. **本地固定版本和工作负载。** 锁定 FlashInfer、vLLM、SGLang 的 commit/依赖；准备 Qwen3-8B 与选定 attention backend 的真实请求轨迹，包含短/长上下文、低/高并发、request churn、chunked prefill、prefix 命中及支持时的 speculative decoding。脚本记录 checkpoint hash、模型配置、warmup、图模式、显存、请求生成方法和 raw trace。
2. **首轮租卡先做根因实测。** 同卡记录 `plan()`、metadata、D2H/H2D、算子、GPU idle 与整步耗时；用连续批处理和多步 draft 触发计划变化，并测试异步/图模式正确性。GPU profiler 计数器需先检查权限；没有权限仍可用 CUDA Events/Nsight Systems，但不报告未测的 HBM/SM 利用率。
3. **先实现论文机制的最小闭环。** 一个 batch/update 流里维护两个以上 in-flight 计划，GPU 增量更新并安全发布；与完整重建、双缓冲修复、原有 fast path 比较。必须有数值对照和 race 压力回归，再看端到端，不用微基准峰值推断服务加速。
4. **阶段性决策。** 若首选题的端到端成本主要落在 plan/同步/host idle，就推进 vLLM 接入、跨模型和 SGLang；若无明显缺口，转测第二题的图断点。两条题都要先测强基线，但无需在立项前证明确定能赢。真实负结果也是正确的选题决策。

论文评价至少包含：同卡强基线、真实公开模型、真实/可复现请求分布、算子与端到端双层计时、TTFT/TPOT/吞吐/P95、显存、精度与并发正确性、失败案例和跨架构验证。A100/A800/H20 是有效研究平台；不要把 H200/SM100 结果未经测量外推。

## 对三个研究问题的回答

- **RQ1：** 通用分页、在线 softmax、动态 tile/dispatch、MoE 形状选核、泛化 mega-kernel 与混合 prefix cache 都有跨年强先例；可研究空间落在真实引擎与算子接口中的**动态状态、增量计划及安全图执行**。
- **RQ2：** 首选 FlashInfer + vLLM/SGLang 的增量异步 attention plan；备选 SGLang/vLLM 的混合有状态 prefill 图安全执行。前者贯通算子调度与引擎生命周期；后者抓住公开的大幅 host idle 问题。两者都需要算法/协议和端到端证据，不能以单个 issue 修复冒充论文。
- **RQ3：** A100 40GB 可以启动 Qwen3-8B；A800 80GB/H20 96GB 支持更大模型/长上下文；DeepGEMM 需要 H20 等 SM90。第一轮买的是**瓶颈归因和正确性证据**，不是提前租满 GPU 做大矩阵。
